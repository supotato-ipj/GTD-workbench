# 容量参数的初始化与调校：agent 建参数，用户点头才改

> **Status**: accepted（2026-11-07）· 修订（2026-11-07）：追加窗口「类」字段、惰性的估时系数与「日清只扣窗口内成本」口径，见文末「修订」节 · 修订（2026-11-08）：追加预计耗时的单位口径（专注时长的单位是**秒**），见文末第二个「修订」节 · 配套 [ADR-0009](0009-工作台是焦点引导器.md)、[ADR-0010](0010-焦点资格与排序.md)

## 背景

焦点引导器要在顶部回答两件事：**今天还剩多少可排时间**、**这一件装不装得下**。这些数来自一份容量账：一天里哪些时段能装活、每天必须还清的固定成本有多少、外部插单要预留多少、一个深度块有多长。

这份账此前只存在于一份本地文档里，工作台一个字都没显示。v2 要把它显示在主位，就必须先定清楚三件事：**它从哪来**、**谁来改**、**改了怎么生效**。

## 决定

- **容量参数是本机机读文件**，由**会话里的 agent** 在**初始化流程**中建立，在**周回顾**时提议修订，**用户点头才改**。
- **只存输入，不存推导值**：可排时间由插件用「窗口时长 − 日清成本 − 插入损耗」实时计算，不落配置。
- 工作台**只读**这份配置，并在顶部显示「**参数定于 &lt;日期&gt;**」。
- **公开仓库只提供 schema 与通用默认值**；真实数值属于个人工作容量，不进公开仓库。
- **调参必须经会话确认**，不做自动化改写。

配置形状（决策密集，故内联；示例值为虚构）：

```jsonc
{
  "定于": "YYYY-MM-DD",
  "窗口":   [{ "起": "09:00", "止": "12:00" }, { "起": "13:30", "止": "16:00" }],
  "不可占": [{ "起": "12:00", "止": "13:30", "说明": "午休" }],
  "日清":   [{ "名": "示例固定成本", "时段": "09:00", "成本分": 15 }],
  "插入损耗分钟": 45,
  "深度":   { "单日上限分钟": 180, "单日配额": 1, "估时系数": 2 },
  "番茄分钟": 25
}
```

字段语义：**窗口**是每天真正能装活的那几段工时；**不可占**是从窗口里扣掉的不可支配段；**日清**是当天必须还清的固定成本清单（每条带时段与成本）；**插入损耗分钟**是外部随时占用、无法事先安排的预留；**深度**一组是深度动作的单日上限、单日名额与估时系数。

## 理由

- **参数必须由"知道用户一天怎么过"的会话建立**，而不是由代码里的默认值猜。默认值是通用形状，不是这个人的一天；猜出来的数字比没有数字更危险，因为它看起来是准的。
- **只存输入不存推导值**：推导值会与输入不同步——改了窗口忘了改余量，两处数字就开始打架。实时算则永远只有一份真相。
- **用户点头才改**：容量参数是关于用户生活的判断，不是系统内部旋钮。自动改写等于让系统替用户决定他的一天怎么过。agent 可以提议（周回顾时拿着这一周的实际执行情况说"这次可排时间似乎偏乐观"），但改不改由用户说。
- **工作台只读配置**：工作台不该长成第二个需要维护的地方（[ADR-0006](0006-工作台是只读视图.md) 的"不写本地文件"这条硬护栏在 v2 仍然成立）。参数写口属于会话。
- **显示「参数定于 &lt;日期&gt;」**：顶部那个数是工作台说得最肯定的一句话。让用户看见它多久没校准，比让这个数消失更有用——它是"这个数还准吗"的入口。
- **公开仓库只放 schema 与默认值**：仓库读者能看懂形状、能改代码，但没有看到任何一个人的真实容量。

## 代价

- **首次使用多一道初始化流程**：参数建立之前，工作台给不出剩余时间。必须显示"未设定"（而不是 0、也不是猜的数）——猜的数会被当成准的数用。
- **调参滞后于生活变化**：日程换了而参数没改，顶部数字会开始骗人。"参数定于 &lt;日期&gt;"是缓解手段，不是消除。真正的修复依赖周回顾时有人记得提这件事。
- **工作台上没有参数编辑入口**：要改参数得回到会话。这是有意的，但意味着"改参数"这件事比"勾完成"多绕一圈。
- **参数是本机文件，跨设备不跟随**：同一份参数在另一台机器上不存在，初始化流程得重跑一遍。
- **窗口与日清的时刻粒度是分钟**：写得越细越准，但也把"按天/按周"的使用者逼进更细的记账。默认值应给粗粒度，让初始化流程按实际情况细化。

## 修订（2026-11-07）：窗口的「类」、惰性的估时系数、日清只扣窗口内成本

> 本节是**追加**：上面「配置形状」那段原文不改写，只在这里补三条实施中定下来的口径。
> 与原文冲突的地方，以本节为准。

实施这一票时，配置形状与计算口径补了三条。原文的形状缺一个字段，口径也少分了一拨成本。

### 一、窗口条目上的 `类`（对上文形状的扩展）

上文那段内联形状的 `窗口` 条目只有 `起` 与 `止`。实施时多了一个字段：

```jsonc
{ "起": "09:00", "止": "12:00", "类": "连续" }
```

- `类` 取 `'连续'` 或 `'可打断'`，**不写按 `可打断` 算**。
- 用途：区分「这一段适合派深度活」还是「适合派事务活」——
  连续窗口优先派深度，可打断窗口派事务（[ADR-0010](0010-焦点资格与排序.md) 的「时段驱动」）。
- 形状之外的键一律不认：多写一个不认识的字段，整份配置被判无效（见下「整体退回」）。

### 二、`深度.估时系数` 是惰性字段，现在不参与估时

上文形状里的 `深度.估时系数` 保留，**但它已经不参与估时**了。

- 估时改用滴答任务自己的专注估算字段：`focusSummaries.estimatedPomo × 番茄分钟`。
- 系数还留在形状里，只是为了不破坏既有配置——**不要以为它还在起作用**。
- 番茄分钟是参数（来自本机配置，缺则用通用默认值 25）。

### 三、日清成本分两拨：只扣落在可用窗口内的那些

上文写的是「可排时间 = 窗口时长 − 日清成本 − 插入损耗」。这条现在要分清：

- **顶部「今日日清未还几笔」统计的是全部日清项**——不管它的时段在不在窗口内。
  日清是当天必须还清的固定成本，落在窗口外也是今天要还的。
- **只有落在可用窗口内的日清成本才从可排时间里扣。**
  落在窗口外的（例如傍晚到件、那个时刻本来就不装活的固定成本）**不占可排时间**：
  它不在工作窗口里，没有挤掉任何可排的活。
- 「可用窗口」= 窗口扣掉与「不可占」重叠的那部分。落在不可占段里的日清项，
  同样不算落在可用窗口内。
- **插入损耗仍按全天全额预留**（保守口径，不变）。
- **剩余可排时间为 0 或负时返回 0**，不返回负数。

### 四、读取与降级（本机配置怎么进来）

- 本机配置放在**仓库根 `local-config.json`** 的**「容量」** 字段里（整份容量参数）；
  这个文件被 `.gitignore` 挡掉，真实数值不进公开仓库。
- 公开仓库里只提供 **schema**（`app/capacity.schema.json`）、**通用默认值**与**虚构示例**。
- 读取**每次都重新读盘**（不缓存）：改完配置 → 刷新页面 → 立刻生效。
- **要么整体有效，要么整体退回通用默认值**：字段缺失、类型不对、时刻格式不对、
  窗口起止颠倒、多一个不认识的字段、文件读不到——一律退回，不抛、不让工作台起不来。
  不做「半坏的配置」：半坏的配置会算出一个看起来准、其实错的剩余时间
  （同上文「猜出来的数字比没有数字更危险」）。
- 退回之后 `capacity.asOf` 为 `null` = **未初始化**，界面据此显示「参数未定」——
  于是「配置写坏了」是看得见的。

## 修订（2026-11-08）：预计耗时的单位是秒

> 本节是**追加**：上文「二、`深度.估时系数` 是惰性字段」里写的
> `focusSummaries.estimatedPomo × 番茄分钟` 原文不改写，只在这里补齐另一半口径。
> 与原文冲突的地方，以本节为准。

上一节说估时改用滴答自己的专注估算字段，但只写了番茄数那一条。实施时发现另一半
（专注时长）也在同一个结构里，而它的**单位是秒**——滴答 CLI 的 `task update --help`
写明：`--estimated-duration <seconds> 预计专注时长（秒）`。

### 一、口径

- 估时分钟 = `estimatedDuration ÷ 60`（**秒**换算成分钟，保留两位小数，不留浮点尾巴）；
  没有这一项时 = `estimatedPomo × 番茄分钟`（番茄分钟来自本机容量配置，缺省 25）。
- **取值优先级：`estimatedDuration` 在前**——它比「几个番茄」更接近真实时长；番茄数作备选。
- 两个都没有（或都为 0）= **未估算**（`null`，不是 0 分钟）。
- 估时口径只有**一个入口**（`app/lib/capacity.js` 的 `estimateOf`）：便贴、行动卡与
  「接下来」队列的估时都从它出，别处不再各算一份。

### 二、为什么

- **单位不是猜的**：口径来自滴答 CLI 的帮助文本。把「秒」当「分钟」会让一条两分钟的
  捕获显示成 0.03 分钟、让五十分钟的动作显示成 0.83 分钟——「装得下／装不下」的判断
  整个失真（这正是本 ADR 反复说的「猜出来的数比没有数更危险」）。
- **两分钟规则因此才够得着**：番茄数最小 25 分钟，永远大于两分钟；
  只有走专注时长那条路（120 秒 = 2 分钟）才可能落进两分钟阈值。
- **「未估算」与「0 分钟」要分清**：没估时就不能说它两分钟能做完（规格故事 15）。

### 三、代价

- **依赖滴答侧的单位声明**：口径来自 CLI 的帮助文本。滴答若改了单位，工作台会跟着错——
  这条依赖写在代码注释里（`estimateOf`），改动时要一起看。
- **专注时长优先于番茄数**：一条同时带番茄数与专注时长的动作按专注时长算。
  两者不一致时（用户改了专注时长、番茄数没动）以专注时长为准——它更贴近真实。
- **秒换算成分钟会出小数**：两分钟是 2 分整，但 90 秒就是 1.5 分。保留两位小数，
  不四舍五入到整分——四舍五入会把「两分零一秒」说成两分钟。

# 工作台是只读视图，完成情况以滴答勾选为准

> **Status**: accepted（2026-11-05）· 修订（2026-11-07）：追加「完成」「改期」两个写口，见文末「修订」节

## 背景

要做一个可视化的任务梳理工作台：左栏有入口，画布上用便贴纸和纸箱展示各类工作任务的完成情况、当前工作计划和未来任务。

设计过程中被问到两个都会改变成品形态的问题：

1. 工作台能不能改数据（拖拽换容器、勾完成）？
2. 「完成情况」要不要区分"勾了"和"真做了"？

第二个问题的背景是这个项目已经付出代价学到的两条结论：**勾选在两个方向上都会失真**——一次是"真做完没勾"，一次是"没做先勾"（同一时刻批量勾掉三条）。按计划本来会做双口径：滴答勾选只算"声称完成"，日总结和证据另算"已核"，并为此建一份本地核销台账。

## 决定

- **工作台只读**：不写滴答，也不写任何本地文件。它是视图，不是编辑器。
- **完成情况 = 滴答 `status=2`**。勾了就算完成，不设第二口径，不建核销台账。
- **不提供拖拽写回**。便贴可以"拿起—晃一晃—弹回原位"，手感归手感，位置归位置。

## 后果

- **接受勾选失真的代价，且这条要写进验收口径**：画布会把那批批量勾选算成完成。工作台不试图纠正，也不提示"这条可能是批量勾的"。
- 工作台**不能成为判定工具**。判定仍然发生在会话里，由 agent 承担（ADR-0004 的分工不变）。拖拽判定台是另一件东西，本工作台不做。
- 换来的是 ADR-0003 那条教训的规避："两处同步必然漂移，漂移之后两边都不再可信"。只读视图不存在同步问题。
- 日总结里"真账"那一层的信息（已交付 / 半交付 / 不可信记录 / 真欠账）**不进画布**。它留在 markdown 里，需要时读文档，不在工作台里另建一份口径。
- 日后若要改回双口径，必须先回答"已核"标记存在哪、以及它与滴答勾选冲突时以谁为准——这个问题在本次设计中被明确搁置（工作台一个文件都不写）。
- 画布上唯一会自己动的地方是动画（见 [ADR-0007](0007-画布结构六箱一天轴.md)）；动画演的是已发生的变化，不产生新的判断。

## 修订（2026-11-07）

工作台改为焦点引导器（见 [ADR-0009](0009-工作台是焦点引导器.md)）后，主位行动卡需要两个写口。**上面「决定」节的三条继续有效**，本次只追加写口：

- **保留一：不写本地文件**。工作台仍然一个本地文件都不写，包括容量参数——它只读。
- **保留二：完成 = 滴答勾选**。完成口径不变：单口径，不建核销台账，不提示"可能是批量勾选"。写口「完成」写的就是滴答 `status=2`。
- **保留三：不做拖拽落位**。不提供拖拽换容器、不提供自由落位；改期走显式写口，不走拖拽。
- **追加：允许两个写口**——「完成」（写滴答 `status=2`）与「改期」（写滴答 `dueDate`，粒度到天）。
- **「跳过」是零写入**：纯视图状态，刷新后回来。它不是第三个写口。

### 理由

焦点引导器的默认形态是"现在该做哪一件"，这一形态天然要求"做完了"和"现在做不了"这两个动作能在卡上直接发生，否则用户每做一件事都要回到会话或滴答再回来一次，工作台就退回成一个只能看的板子。

写口只开两个，是为了让"工作台会改我的数据"这件事边界清楚：只有勾完成和改截止日两件确定、低风险、可撤销的事能在这里发生，其余一律回会话。

### 代价

- "只读视图"这个标题不再覆盖全部事实：**工作台不再是纯只读**。仍然不写本地文件，但会写滴答的两个字段。旧标题保留是为了不重写 ADR 记录，实质含义以本节为准。
- 写口会把工作台从"零同步风险"的位置挪开：既然能写，就要处理写失败（未登录、参数非法、目标不存在），错误必须显式呈现，不能静默。
- 写失败会带来一种新的用户困惑——"我以为完成了"。因此写失败必须明确报原因，且失败时卡片不得消失。
- 写入仍走与读取同一条 HTTP 契约（读 `GET`，写 `POST`），不为写口另造一套接缝。
